# 成品售出流水：版本迁移与上线核对表

状态：代码及自动化回归完成，**尚未完成 Android/Windows 双设备真机验收，不允许直接发布或合并生产构建**。

## 设计约束

- 每次售卖的 `SaleReceipt` 含唯一 ID、时间、当时平台、成交基础价格、合计手续费、实际收入和历史估算标志。
- `saleReceipts` 是升级后的财务事实来源。`saleRecords` 和 `soldCount` 为兼容旧数据继续保留，在新版同步读取时由流水重新投影。
- 新流水经 `sale-receipt-delta` 进行操作集增量合并；同一笔销售重传不双计，撤销按不可复用的 ID 删除，删除优先，历史确认后才折算操作。
- **旧历史日期只有时间，不包含原始售价**。本次升级按当时当前商品设置生成估算快照，`estimated=true`，不会伪称实际历史金额。售出详情与日程历史卡片会标注估算。
- 完整数据/备份格式升级至 **schema 8**。新版可读取 schema 7 及早期备份；旧版拒绝 schema 8 备份，避免静默丢失新财务字段。
- 整个系统依旧本地优先、P2P；不新增交易云数据库。

## 必须一起升级的限制

**至少在本次内测发布阶段，所有仍绑定的 Android/Windows 设备都必须升级到支持 schema 8 / saleReceipts 的客户端后，再继续双端同步。**

旧版应用不知道 saleReceipts 字段，无法对新流水做可靠的新增、撤销与冲突处理。新版虽然会双写旧的 soldCount/saleRecords，仍无法保证旧客户端在编辑同一成品后不破坏流水；这不是警告就能解决的兼容性问题。本次没有伪称支持混用客户端。

建议上线策略：先在每台设备导出独立完整备份 → 确认全部设备完成更新 → 统一启动同步。无法升级的设备先停止同步，等待更新后加入。

## 自动化验证

- 历史 100 元、200 元两次交易，改售价、平台、手续费不回算旧款。
- 手续费计算遵守既有米画师取整、画加阶梯规则。
- 老 7 版日期记录变成估算交易，并保留原日期；schema 8 读写往返。
- 手机、电脑分别离线售出后合并得到两笔；重复合并不双计。
- 撤销后再同步、操作压缩并从滞后设备重放，不能复活已撤销销售。
- 单次/多次售卖切换与售出次数回退。
- 成品参考图完整备份不能遗漏（由审计 PR #23 修复）。
- Beta 发布 CI 检查 Flutter 全套、静态分析和激活码服务并发测试。

## 真实设备验收（尚未执行）

1. 保留升级前真实数据备份；各设备在未连接时分别安装新版，确认原历史售出日期和“估算”标记。
2. 手机售出一次、电脑售出一次，分别设置不同价格、平台和手续费；恢复连接后，两台同步得到两笔历史收入、统一时间和相同平台分类。
3. 一端撤销售出；断开另一端、重新连接及重启，确认撤销永久生效。
4. 在多笔出售后修改当前商品价格、手续费或平台：月度总计、平台分布、五个月趋势、日程每日合计、售出列表收入一致。
5. 分别 Android/Windows 导出 ZIP、删应用数据后恢复，核验用户、成品、流水、参考图及所有标记；模拟恢复失败后确保原数据不动。
6. Android 真机跨零点、时区切换测试；时间应使用本地日期展示，UTC 存储，避免晚上售出的单落到隔天。
7. 旧版客户端绝不参与本次新流水同步；需要兼容旧设备时应在专门评审中设计真正的版本握手和双写协议，而不是假定兼容。
8. 出正式内测包前，把功能修复写入 `冒险者新见闻` **实际发布 build 号**，不要预占未来版本号或改动其他窗口的发版顺序。
