## 第二轮：参考图删除与大图备份防护（2026-10-10）

这轮改动在独立售出流水/审计分支进行，尚未合并主线。

### 已实施：避免离线设备丢参考图

- 原版排单、成品详情页在移除已经保存的参考图后，立即删除 Syncthing 共享根目录中的原始文件；成品单条/批量删除和归档批量删除也会删除实体图片。其他离线设备可能仍持有图片元数据，重连后造成“引用还在但图片不存在”。
- **现在已统一调整为「元数据逻辑删除」**：从已保存排单/成品移除图片或永久删除实体时，不会立即物理删除同步图片文件；归档清理弹窗明确说明图片可能继续占用磁盘空间。
- 新建/编辑页中**尚未保存**的新导入参考图，在用户取消编辑时仍会清理。独立 `OrderReferenceImageStore` 记录当前会话实际导入的草稿路径，保存时显式 `markCommitted`，防止旧调用者误将其他已保存的共享图片当草稿删除。
- 新增测试证明已标记保存的参考图即使被错误送到草稿清理 API 也不会被删除，同时未保存草稿仍能移除；完整备份只包含当前元数据实际引用的图片，避免把留存的孤儿图片打入备份。
- **保留限制**：已经从元数据移除的图片原文件暂时保留在 Syncthing 数据目录，不自动释放空间。建立「所有仍绑定设备确认不再引用 + 安全确认水位 + 可恢复清理」之前，不做猜测式自动 GC；极大的美术参考图会暂时增加磁盘占用。

### 已实施：在 ZIP 解压前检查清单与资源

- 先验证并读取 `backup.json`（最大 32 MiB，避免把极端异常 JSON 清单直接读入内存），从当前排单与成品引用中构建**准确的资源路径和声明大小清单**。
- 每个 ZIP 图片文件必须被清单引用，且 ZIP 解压后预计大小应与清单一致；引用缺失、路径异常、未引用的额外资源、异常大小一律**在解压前**拒绝。
- **不限制正常参考图原文件的体积**，仍支持单张 1 GiB 及以上图片；图片内容继续由库流式解压到磁盘，导出继续按流写 ZIP。
- 新增恶意附加资源、错误声明尺寸的测试；现有排单、成品实际 ZIP 导出/恢复测试也保持通过。
- **仍待专项完善**：ZIP 元数据如果被恶意伪造，实际解压流可能超出预期；完整的逐字节写入预算与空间不足回滚仍须验证，不能因为解压前检查通过就宣布彻底消除所有 ZIP bomb 风险。

### 仍未动的大幅重构

- Syncthing 目录 O(N²) 反复扫描优化、所有设备安全确认后的参考图二进制 GC、备份恢复时的大图重复磁盘复制以及跨 Android/Windows 真机故障恢复，**尚未实施**。涉及恢复原子性与并发协议，不能在未验证时贸然替换。


## 第三轮：单记录同步读取与超大资产恢复优化（2026-10-10）

### 已实施

- `SyncRecordStore.readMergedRecord` 以前每次读取一个指定 ID 都遍历并解码同一类型目录的**全部 JSON 记录**，本地排单、成品逐条修改可能扩大成 O(N²) 次解码。现在根据稳定的 Base64 文件名只解码该 ID 的规范文件与 Syncthing 冲突副本；对非常规命名的老文件仍保留回退解析，保留向量时钟/字段冲突/合并与规范化逻辑。
- `deleteRecord` 的历史清理也只读取相关记录副本，不再解析同类全部历史记录；每 4 秒一次的**全量远端对账**仍沿用原有 `readAllMerged`，避免遗漏离线远端更新。
- 新增多达 250 个无关记录共存、手机电脑冲突副本合并、不同字段自动收敛、非常规旧文件命名的回归测试。
- 原来 ZIP 导入恢复会先将 Syncthing 活动目录重命名为 `previous`，再开始大量复制现存图片与 ZIP 解压图，导致共享根目录暂时不可用的时间随美术文件大小增长。
- 现在**在切换目录之前**完成导入 ZIP 资源的阶段性复制；进入切换阶段后只补充此前同步目录特有的文件。如果备份和当前目录有相同路径，以备份内容为准，不再重复写入同一份大图。
- 新增恢复覆盖测试：备份图片与旧图片重名时备份优先、离线设备可能引用的旧独有图片仍保留；如果发生资源路径文件/目录冲突且切换阶段失败，原活动目录、原图片和排单历史均应回滚。
- 恢复期间增加同一账号跨 `SyncRecordStore` 实例的进程内等待保护，避免其他页面的 `rootDirectory` 将正在写入的大图 staging 误当成崩溃残留删除。恢复完成后再读取当前目录状态；早期创建 staging 失败也做清理。

### 有意保留的限制

- 这不是 Syncthing 协议重构；后台每 4 秒全目录对账仍保留，用以避免 Android/Windows 系统目录事件丢失造成远端更新长期不可见。若继续优化为增量轮询，必须保留定期全量兜底并加入真实双设备断网/杀进程测试。
- ZIP 解压临时目录和活动同步目录在恢复期间仍需要额外磁盘容量。**本轮明显减少重复文件复制及同步目录的停用时间，但还没有彻底消除 1GB 图片同时存在原文件、解压副本与阶段副本的峰值磁盘占用。**完全免复制移动方案涉及文件系统卷与断电回滚，应作为独立评审，不能冒险引入。
- 进程级等待保护不代替真正的多进程 Windows 文件锁；其他程序（Syncthing 或 Windows 索引器）仍可持有句柄。需要真实 Windows + Android 大图恢复及模拟中断验证。


## 第四轮：ZIP64 依赖与解压硬预算（2026-10-10）

### 解码器升级

- 完整备份使用的 `archive` 从 `4.3.0` 升级并在 `pubspec.yaml` 固定最低为 `4.4.0`，`pubspec.lock` 的 SHA256 校验值从 GitHub Actions 中实际由官方 Dart/Flutter 包解析器生成的锁文件核对，不手工编造。其余已锁定依赖保持原版本。
- 官方 4.4.0 修复特制 ZIP64 文件声明压缩大小溢出绕过流边界的问题，还加强流式解码和编码能力。测试需与 Android/Windows 实际文件操作配合。
- 用于解析官方锁文件的一次性 GitHub Actions 工作流在使用完毕后从 PR 的最终文件树中移除。

### 把限制从「解压前推测」变成「写入时强制」

- 原代码用 `extractArchiveToDisk` 批量解压；上游库的某些提取路径会捕获并忽略单文件解码异常，业务层只靠最终尺寸可能错判部分损坏。现在逐一调用 `ArchiveFile.writeContent`，任何解码异常直接中止整个导入并清理临时文件，不触碰用户在用的数据。
- 新 `BoundedArchiveFileOutput` 在文件写入过程中统计**实际解压字节数**：不能超过该成品/排单图片在备份清单中的声明大小，且解压结束必须恰好匹配，禁止利用伪造 ZIP 元数据写爆磁盘。**没有给正常 1 GiB、2 GiB 等大型参考图设置固定上限**，内存仅保留小块写入缓存。
- 备份清单 `backup.json` 也使用同样的受限输出，最大 32 MiB，在解压完成和 CRC 校验之前不会将不受信任内容直接读入内存。
- 对每张图片和清单的 ZIP CRC32 做增量校验，即使恶意破坏文件内容但保持大小不变，也会拒绝恢复。校验覆盖常规字节写入和压缩解码器的后向引用。
- 新增精确上限、超过上限、零长记录、后向引用、CRC 和 ZIP 原始内容同尺寸破坏测试。实际 CI 结果以对应最新 SHA 为准。

### 剩余限制

- 本轮不会自动清除被所有设备已删除的美术文件：跨设备安全 GC 仍需所有绑定设备共享确认水位、退出设备处理和保护期策略，不能简单删除共享目录文件。
- ZIP 导出与跨设备完全恢复仍需占用压缩包和临时目录的磁盘空间；恢复时 ZIP 解包和阶段目录仍可能形成两份大图，此轮未引入未经真机测试的跨文件系统移动/硬链接。
- 大文件中断、Windows 文件句柄占用、Android 空间不足以及从旧版同步数据升级到新版售出流水的完整端到端验证仍未完成。


## 第五轮：完整发码历史与大图零重复复制恢复（2026-10-10）

### 激活服务 + 发码器一起修正历史分页

- `GET /v1/licenses` 不再只给最近 500 条，而是保留每页最多 500 条，通过不可变全局编号 `id` 降序 keyset 游标 `nextBeforeId` 和 `beforeId` 继续拉取更旧历史。不能用 OFFSET，因为拉取途中有新激活码进入可能改变偏移。
- 接口仍要求管理员 Bearer token；保留作废记录的隐藏逻辑；对不合法的 `limit` 与 `beforeId` 返回明确 400，不让 SQL 运行异常直接演化成 500。
- 发码器现在请求**所有分页**并检查游标单调递减、同页与跨页编号去重，在整个加载成功后才交由 `LicenseIssuerStore` 更新磁盘历史。任何部分网络失败/坏响应都会保留原缓存。
- 为了不让尚未部署的**旧服务**悄悄返回残缺历史：若响应已经满 500 条但没有 `nextBeforeId` 字段，新发码器提示需要先升级服务端，**不会覆盖原本更完整的本地历史缓存**；旧服务记录不足 500 条仍可兼容。
- 新增服务端 1205 份历史（含一份作废）、分页中途又生成新码、无重复无遗漏、无效游标/无管理员权限的端到端 HTTP 回归；发码器 Dart 端新增本地 HTTP 服务测试，覆盖超过 1000 条分页、重复编号/不前进游标/旧服务器满 500 等。
- **服务部署顺序**：必须先把 `license.apixb.top` 的服务部署到包含此改动的代码，验证线上超过 500 条，然后再发布新版发码器。当前仅是独立 PR 代码及 CI，**未部署到生产服务器**。

### 大图片 ZIP 恢复避免二次复制

- 增加显式 `transferImportedAssets` 参数，默认 `false`，以维持所有其它公共调用者「复制源文件、源文件保持原样」的契约。设置页在恢复自己临时解压的完整 ZIP 资源时才设置 `true`。
- 目标 staging 目录与临时 ZIP 解压目录**在同一卷**时，使用文件夹 `rename` 转移资源所有权，不复制可能 1GB+ 的完整文件；跨卷或 Windows 句柄导致重命名失败时，自动回退成原来安全的 `_copyDirectory`。
- 保留旧账号同步目录与 ZIP 资源重名时的「备份优先」，离线设备唯一图片保留；恢复中途失败时必须回滚同步原目录、订单历史，若暂存图片是从临时来源转移还应移回来源供再次尝试。
- 新增目录转移和恢复失败回滚测试，并保留旧默认复制 API 的用例。
- **空间占用边界**：恢复仍需要 ZIP 文件本身及解压后的图片。同行/同卷重命名消除了导入图片另一次完整复制；跨卷仍会复制并要求足够剩余空间；原本同步目录已有的离线唯一素材还会进行安全的补充复制，不能宣称所有场景峰值磁盘占用都减半。仍需在真实 Android/Windows 盘空间不足、正在同步、杀进程中断情况下验收。

### 此轮仍不做无依据的参考图物理删除

`gc-acks` 目前主要确认同步记录的相同内容签名；并不足以证明每一个曾离线的设备对单独二进制素材的引用都已安全收敛。所以这一轮继续保留已经逻辑移除的原图，不偷换成按天数直接清理；需设计独立的素材引用/删除确认协议及解绑设备处理流程之后才能进行自动磁盘回收。


## 第六轮：注册和激活请求限流（2026-10-10）

- 发现原部署脚本和示例 Nginx 对外公开 `/v1/admin/register`、`/v1/activate` 未设置速率限制。新增两条仅限敏感接口的按 IP Nginx `limit_req` 规则，返回明确 429；限流 zone 放在 HTTP 全局配置，endpoint 配置放在 server 中。所有其它接口与健康检查不被这两项限制影响。
- 管理员注册默认每分钟 3 次/单 IP、突发 3 次；激活接口每分钟 30 次/单 IP、突发 15 次。这个数值是防撞库初始配置，仍须真实部署针对移动运营商共享 IP 做负载与误限观察。
- 发码器及普通用户注册 API 均在试图解析 JSON 前识别 HTTP 429，这样 Nginx 返回的默认 HTML 错误页不会变成「无效 JSON」；新增真实本机 HTTP 429 回归。
- 另新增部署 Bash `bash -n` 语法与 Nginx 配置片段一致性测试，手动部署样例与自动化部署均包含同样的限制。
- **此 PR 不直接修改线上 VPS 的 Nginx，也未重启生产激活服务。** 需要先备份现有部署配置，实际运行 `nginx -t`，确认有 `conf.d` HTTP include，再在低峰 reload 并做真实注册/核销验收。切勿把仓库配置合并误认为服务器已经生效。

## 第七轮及精简复审：参考图回收与同步历史压缩

审计分支曾为了所谓「安全」额外加了 30 天图片保留、24 小时删除记录保留、72 小时 ACK 过期及每 6 小时刷新 ACK；这些时限没有提供可验证的额外安全保障，反而制造垃圾、额外文件写入和复杂状态。**已在代码中全部移除，不再使用时间作为删除授权。**

**目前实际保留的安全条件：**

- 仅在已保存的排单/成品实际解除图片关联后登记待回收文件；不扫描并删除全部「当前无引用」的图片，以免误删尚未保存的新导入素材。
- 所有仍绑定设备必须支持图片清理协议、确认相同的绑定成员集合和完整同步记录签名；若离线、旧版或记录冲突，暂不物理删除。
- 删除前重新检查当前所有排单/成品是否仍引用图片，以及文件路径是否存在越界/符号链接。确认后**不再强行等几天**，下次检查即可清理。
- 未变更的设备确认文件不重写；不需要所谓「保活 ACK」。普通 P2P 同步仍按原有 4 秒机制运行，参考图清理最多每 30 秒检查一次；无待回收文件时跳过昂贵的记录签名计算。
- 旧同步历史删除标记也取消额外 24 小时等待：只有全部绑定设备确认同一个删除标记时，才删其历史 JSON 记录；未确认者继续保留。
- 单条记录读取不再为猜测性「非规范旧文件名」解析所有无关 JSON；完整同步扫描仍可恢复这类文件，保留对 Syncthing 正规冲突副本的处理。

**故意保留且有可验证用途：** 操作唯一 ID 与向量时钟（防止并发覆盖/多次记账）、仍绑定设备的 ACK（防止离线重现）、原子文件写入及备份校验（防止数据损坏）。不为了「更安全」再叠加同意义的计时器、复制和重复检测层。
