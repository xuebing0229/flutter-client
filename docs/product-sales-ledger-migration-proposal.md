# 评审提案：成品售出流水与历史收入冻结（仅方案，未实施）

审计时间：2026-10-10  
状态：**等待产品负责人批准激进重构**  
关联：`docs/prebeta-code-audit-20261010.md`

## 1. 源码证据及已确定的错误

- `FinishedProduct.saleRecords` 的类型是 `List<DateTime>`，每条记录只有时间，**没有交易的当时售价、手续费和真实收入**。
- `ProductStore.markSold` 每次增加 `soldCount`、向 `saleRecords` 加入当前时间。
- `ProductDetailPage._save` 可调整成品售价、平台、手续费及售出次数；减少售出次数时直接移除列表末尾的日期。
- `StatisticsPage._productSalesFor` 对每条当月 `saleRecords` 重复使用 `product.realIncome`（**商品当前价格**），月度趋势图同理。
- `SchedulePage._dailyIncomeOn` 也在历史日期逐项使用 `sale.product.realIncome`。
- `SyncMergeEngine` 把 `soldCount` 作为 `sale-delta` 增量操作，并用 `saleRecords` 的字符串列表写入新增/撤销记录；`compactAcknowledgedOperations` 可以将操作折算回基线。
- 备份 `AppBackupData` 直接将售出日期存为字符串列表；仅改 UI 计算无法恢复历史金额。

**复现**：一件多次售卖成品 9 月 1 日售出，真实收入当时为 100 元；10 月售价修改为 200 元；再查看 9 月收入，现有计算会以 200 元重新计算那笔销售。因此日程收入、平台分布与月度趋势可能一起漂移。

## 2. 第一本原理：成品≠交易

成品是一个可以修改的「商品资料」：名称、当前报价、当前平台费率、图片、描述、是否归档。

每次售出是一个**已经发生的财务事实**，至少必须有：
- 稳定唯一 `saleId`，不能把售出时间当成主键（两次售出可能同一毫秒）。
- `productId`、`soldAt`、`netIncomeAtSale`（当时实际收入）。
- 必要时保存 `platformAtSale`、`grossPriceAtSale`、手续费金额/规则快照，以保证之后变更平台、真爱折扣或手续费也不影响历史归属和结算。
- `status`：有效/已撤销；撤销需要可同步的操作标记，而非简单删掉一行。

**统计源头应为交易，不应为成品当前状态**。不引入云服务器或中央流水账，交易仍保存在本地设备并通过既有 P2P 同步。

## 3. 推荐架构（待批准）

```text
ProductCatalogEntry  (当前商品，可编辑)
  └─ SaleLedger  (单独交易层；纯领域逻辑)
       ├─ SaleRecorded {saleId, soldAt, netAmount, feeSnapshot, platformSnapshot}
       └─ SaleVoided {saleId, voidId, voidedAt}  // 可审计、幂等
               ↓
       SaleProjection   → 已售次数 / 历史收入 / 日程 / 月度统计
               ↓
       SyncLedgerAdapter → SyncOperation + safe compaction
```

- 为明确语义，建议 `soldCount` 成为交易视图的**派生值**，杜绝数字和时间列表不一致；单次售卖仅允许一笔有效交易。
- 多次售卖每次写入独立流水，支持两个设备离线各售出一次后合并为两笔；同一事件重传不重复计入。
- 以前的「售出次数 -1」转换为对一笔指定交易的撤销；默认撤销最近一笔以保持现有界面行为。P2P 要保留撤销 tombstone，不能让旧设备重新同步时复活。
- 详情页仍显示当前价格；查看售出记录可显示每笔当时金额。**不改变原有排单/成品 UI 排版**；若需要增加纠错入口，必须另行评审。
- 统计与日程统一调用 `SaleProjection`；删除三处各自推算历史收入的重复逻辑。
- 金额存储需确定统一小数精度和舍入规则；现有手续费公式用浮点数，**未确认前不可偷偷变更金额口径**。

## 4. 老数据迁移与同步风险

最大的约束：现有旧记录仅知道 **售出时间**，历史价格完全不存在。绝不能凭空重建“当时实收金额”。

建议分阶段演进：

1. **保护和备份**：升级前提供完整备份；构建覆盖旧版 `saleRecords`、单次/多次、售出次数回退、多端并发、更换售价及手续费的回归矩阵。
2. **兼容读取**：新版本读取旧记录并保留全部原始 `saleRecords`，不丢日期；按照明确规则将旧日期标记为 `legacyEstimated`，首迁时以当时当前价格形成**估算快照**。用户要能辨认估算与真实交易；不允许悄悄标为真实历史实收。
3. **写入切换**：仅在有升级协议/版本检查后启用新交易流水。**不能**让新版写 `saleEvents`、旧设备仍修改 `soldCount` 而没有转换器；那会造成漏记或双计。
4. **身份确定**：老日期若需要转换为稳定 ID，不能单纯用时间；至少用 `productId + UTC timestamp + repeat index`，且需要验证离线设备有不同顺序/不同历史时的确定性。更稳妥的是兼容层保留旧流水直至完成跨端一致性确认。
5. **冲突语义**：新增/撤销/更正都必须可交换、幂等，跨设备 merge 顺序不影响最终结果；操作压缩前各仍绑定设备必须确认已见过事件/撤销。
6. **验证**：`Flutter analyze`、单元测试、ZIP 备份往返、协议升级、真实 Android+Windows 双端离线冲突、重复同步、恢复旧版备份、大图与断点更新共存。

如果不愿要求用户在多设备上同时更新，须做**双写、旧客户端写入检测、冲突转换**的桥接方案，并证明不会双计；否则应在交易记录版本切换时明确要求两端升级。两种路线需产品决策。

## 5. 为什么不采用快捷补丁？

- 仅为现有 `saleRecords` 增加平行的金额列表，删除一条旧日期、同步合并顺序变化就可能发生错位，**不推荐**。
- 在统计时“取第一次售出时保存的成品售价”无法表达多次售卖各次不同价格；也不能处理补/减款。
- 单纯给 `FinishedProduct` 增加 `lastNetIncome`，会继续篡改更早的交易。
- 删除当前同步里所有 `sale-delta` 机制然后从头写同步，风险过高；应先锁定旧行为和安全压缩语义，再逐步适配新事件协议。
