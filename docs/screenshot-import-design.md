# 截图批量导入：开发基准（2026-10-08）

状态：**分支内开发中；未集成 OCR 引擎，禁止以完成品发布。**

## 入口与体验

- 排单页原「新增排单」悬浮按钮点击后展开「手动导入」「截图导入」。
- 成品页原「新增成品」同样展开，不再要求先选择“排单还是成品”。
- 成品截图导入以**成品橱窗**为单位创建成品：用户先选单次售卖或多次售卖，可在预览逐条调整；OCR 不尝试提取出售次数或售出时间。
- 相册/文件选图支持多张；识别完成展示**纵向紧凑横栏**，一屏多条：状态、原始完整标题、单主、日期、金额、进度/预设、编辑、删除。
- 预览的公共属性有平台、节点预设、手续费；每条可覆写。底部固定导入计数与确认按钮。
- **识别不等于导入**：修正错误、人工确认冲突后，整批原子式提交；任何不完整或低信心字段高亮，不能默默补造。
- **日期精度必须保留**：米画师列表截图仅出现 `2026-10-31` 时，OCR 只知道日期，不能当作午夜截稿。米画师常规「按日定截稿日」可在预览**建议预填 23:59，明显标注“按日截稿推定，可修改”**；快速橱窗（x 天后）等情况不能套用此默认值。订单详情明确识别出 `2026-07-13 21:05` 时须用 21:05，不允许被推定的 23:59 覆盖。这个推定来自用户的经验与所示详情样例，尚不能保证所有米画师类型一律适用。
- 导入预览支持逐条确认或更改时分，也提供**用户主动选择的批量统一时间**（只补缺少时间的行，不修改 OCR 已识别出时分的行）；用户在最终确认导入时认可推定时间才允许写入。对无可靠推定的日期，须由用户明确填写。
- 当前排单模型 `QueueOrder.deadline` 仅支持完整 `DateTime?`。因此 OCR 原始解析在未识别时分前保留日期，`importReadyDeadline` 仍为 `null`。米画师推定 23:59 只能由专门的 `suggestedDeadline` 字段提供给 UI 预选，不等于 OCR 已识别到的准确时分；在最终确认导入前不得偷偷提交推定值。
- 预览点击具体字段可定位回原图 OCR 的对应框；默认不提取订单缩略图作为参考图（尚未获得明确确认）。

## 文字处理

- 保留作品名称全部有效字符，例 `【常驻】 黑白摸鱼头3.0` 不得删前缀或变成 `黑白摸鱼头3.0`。
- 只过滤手机状态栏/导航栏、电量、系统时间，以及可明确辨认的 App 控件等**无关 OCR 行**。
- 使用文本坐标先定位订单卡片，**再**从各卡片中提取单主、标题、日期、金额、交付进度。禁止全屏全局找最近一个价格配最近一个标题。
- 截图可只展示部分卡片，分页、下拉、不同平台皮肤时需“未完成/待复核”提示。
- 平台先自动尝试判定：米画师、画加；依据平台特征文本 + 几何布局，可信度不足不猜。用户可覆盖任何预选。

## 节点策略

- 多套节点预设绝不能仅凭平台决定；记忆键为 **当前账号 + 平台 + 完整单名（比较时折叠空白）**。
- 首次让用户指定节点预设，后续同一作品预选上次指定的预设；每条都可改。
- 若 OCR 提供交付比例，只接受所选预设中的**精确百分比匹配**；不能四舍五入或按“最接近”猜。
- 百分比匹配多个节点时，可用 OCR 的节点名称作二次区分；仍不唯一则回落到预设第一个节点。
- 比例存在但无匹配时，即便节点名称相同也应回落第一个节点，避免错选已完成。没有比例时可使用准确匹配的节点名称。
- 同批导入预览中，用户在**任意一条**订单手动选定节点预设后，同平台同完整单名的全部其他未手动改过预设/节点的条目立即跟随，不受列表位置限制；各自按照 OCR 百分比独立映射。
- 临时批次选择在预览期间生效，取消导入即丢弃；确认导入后才更新跨批次预设记忆。不自动标记交稿。

## 排单去重

- 同一张截图中识别出的不同实体卡片视为独立订单，即使同名单主同日期也不能据此折叠；仅重复解析同一卡片区域属于技术重复。
- 只对不同截图之间、以及新识别订单与已导入/已归档记录之间做疑似重复比对。
- 不同来源图片的「平台 + 单主 + 完整单名 + 截稿日期/时间」相符时，标记**疑似重复**并让用户选择保留两单或跳过；不能自动合并。画加截图中的截止时间通常到分钟（不等于下单时间），米画师可能仅到日期，均不得作为唯一交易 ID。
- 未能识别时间/单主 => 提示待确认，不能凭标题单独“判定重复”。
- 操作：跳过、仍新建、查看/人工选择要覆盖的字段。原订单参考图、补减款、备注等不能被导入空值覆盖。
- 同一平台若真实订单号可识别，则优先作为强标识；画面 OCR 或历史模型不应臆造订单号。

## 成品橱窗识别、去重与双端数据一致性

- **成品截图识别的是不同的成品橱窗，不是交易记录。** 和排单不同，成品橱窗通常没有截稿时间。不能试图拿截图中的日期当成成品售出时间，也不必据截图反推买家、售出次数。
- 同一批图片中（包括同一张截图的多个位置）、不同截图之间，按**平台 + 完整成品名称（仅规范空白）**合并重复橱窗，每个独立橱窗只留一条预览。即便截图里有多个相同橱窗，也只创建一个成品。
- 同时和 App **已有及已归档成品**核对；若同平台同名，则标记“已有成品，默认跳过创建”，允许用户手动查看并决定是否确实是不同成品。千万不能因为截图出现了一次就改动已有的售出次数、售出记录或收入。
- 同名橱窗在多个来源截图中价格不一致时，标记待复核；不自动加价、加售出次数或任意选择一个价格。
- 用户在导入预览选择 **单次售卖 / 多次售卖**；新建的多次售卖初始售出数为 0（除非用户之后在 App 里**主动登记**售出），未来的数量统计继续复用现有 `ProductStore.markSold`、`soldCount` 与 `saleRecords`。
- **不新增 OCR 专用售出事件标识与自动加次数功能**，因为现在不从截图导入售出事件；保留现有手动售出及同步逻辑。以后若要做订单流水导入，再另行设计幂等交易 ID，不混入本期截图橱窗识别。
- OCR 输入不可靠时保持空白并允许用户补填。两端同步依旧按照原有成品的数据结构运作，不凭 OCR 替用户产生收入。

## 引擎与工程分层

- OCR 选择离线、可商用的 PaddleOCR PP-OCR mobile/ONNX 方案为候选；Android、Windows 各自接原生推理桥，复用纯 Dart 的卡片分组和解析/审核逻辑。Windows 必须打包模型随应用安装，不能依赖终端用户第一次联网。
- 模型版本、许可证及模型 hash 固定；先拿用户提供的米画师和画加多卡片截图做准确率验证，不能仅凭基础示例保证结果。
- 图像及 OCR 中间结果仅保留本地；不上传服务端。
- 复杂高风险项目按阶段交付：OCR 引擎稳定性 → 平台卡片分组与字段提取 → 预览 UX → 去重事件与 P2P 同步 → Android/Windows 回归与体积验证。
- 分支 `feat/screenshot-order-import-20261008`；不得 force push 主线，不触发 Beta 发布构建，不覆盖另一窗口的独立提交。

## 验收样例

1. p1 米画师：多卡片；`【常驻】` 前缀完整保留，日期、价格与单主不串行。
2. p2 米画师：无稿价也允许预览，金额为空并要求人工输入。
3. p3 画加：「我卖出的」「当前交付节点」，分割每个卡片；100% 只能映射当前用户选择的节点预设。
4. 排单：同图不同实体卡片保留、多张重叠截图标疑似重复；成品：同图或多图相同橱窗合并、已存在成品默认跳过；不把成品截图变成售出次数。
5. 关闭功能后原数据不丢；备份/恢复、端到端同步覆盖新字段。
